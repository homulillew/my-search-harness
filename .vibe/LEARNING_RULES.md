# AI 编程协作规则：高效开发 + 模块级理解

本项目采用“AI 高效实现 + 人类掌握系统”的协作方式。

核心目标不是让我亲手写每一行代码，而是确保随着项目增长，我始终能够理解：

- 项目的整体架构
- 每个模块为什么存在
- 每个模块为什么这样设计
- 关键技术决策和取舍
- 模块之间如何调用
- 数据如何流动
- 状态在哪里变化
- 代码实际是如何运行的
- 如果未来要修改功能，应该从哪里入手

AI 可以负责大量实现、测试和调试工作，但不能只给我“最终结果”。

每完成一个重要模块，都必须帮助我建立清晰的 mental model（心理模型）。

---

# 一、总体原则

## 1. 不要直接开始大型实现

当我提出一个非简单需求时，不要立即大规模修改代码。

先向我说明：

1. 当前相关代码在哪里
2. 当前系统是如何工作的
3. 这个需求涉及哪些模块
4. 准备新增或修改哪些模块
5. 数据流和控制流会如何变化
6. 关键设计决策是什么
7. 为什么选择这个方案
8. 有哪些可选方案
9. 为什么没有选择其他方案
10. 如何验证最终实现正确

然后给出一个分阶段开发计划。

如果修改较大，等待我确认后再开始。

---

# 二、一个模块一个模块开发

不要一次生成大量互相独立的功能。

优先按照逻辑模块拆分，例如：

```text
模块 A
→ 实现
→ 测试
→ 模块讲解
→ 我确认理解
→ 模块 B
```

一个模块应形成一个可以独立理解的逻辑闭环。

例如：

- 数据模型
- Retriever
- Agent
- Service
- Parser
- Scheduler
- API Endpoint
- 数据库存储层
- 缓存层
- 前端组件
- 一个核心算法

如果一次修改已经大到很难解释清楚，请主动拆小。

---

# 三、写代码前：先建立设计模型

每个重要模块在实现前，先解释设计。

至少包括：

## 1. 模块目标

说明：

- 这个模块解决什么问题
- 为什么需要单独存在
- 它负责什么
- 它不负责什么

## 2. 输入与输出

明确说明：

```text
输入是什么
↓
模块做什么
↓
输出是什么
```

包括重要数据类型和结构。

## 3. 所处位置

说明它在整个系统中的位置。

例如：

```text
User Request
↓
API
↓
Planner
↓
SearchAgent
↓
Retriever
↓
LLM
↓
Parser
↓
Response
```

明确当前模块位于哪一层。

## 4. 依赖关系

说明：

- 它依赖哪些模块
- 哪些模块依赖它
- 是否依赖外部 API
- 是否依赖数据库、缓存、队列或模型

---

# 四、设计决策必须解释“为什么”

不要只告诉我：

> 我准备使用 X。

还要说明：

> 为什么使用 X。

对于重要设计，请使用下面的格式。

## Decision

最终选择了什么方案。

## Reason

为什么选择这个方案。

## Alternatives

还有哪些可选方案。

## Trade-offs

当前方案获得了什么，又牺牲了什么。

例如：

```text
Decision:
使用 Redis 保存短期任务状态。

Reason:
任务状态需要被多个 worker 共享，并且生命周期较短。

Alternatives:
1. Python 内存字典
2. PostgreSQL
3. Redis

Trade-offs:
Redis 增加了一个外部依赖，
但换来了跨进程共享、TTL 和较低访问延迟。
```

对于核心架构决策，不要省略这一部分。

---

# 五、AI 可以自动调试，但需要保留重要知识

AI 可以自己：

- 运行测试
- 修复简单错误
- 修复类型问题
- 修复语法问题
- 修复明显 API 使用错误
- 进行必要的 Debug

不需要每一个 Bug 都让我参与。

但是，如果 Debug 暴露出以下问题：

- 对架构理解有影响
- 原设计存在错误
- 数据流与预期不同
- 出现隐藏状态
- 第三方 API 行为和预期不同
- 并发或异步行为有重要影响
- 修复导致设计发生变化

那么模块完成后必须告诉我：

### Debug 中发现的重要事实

- 原因是什么
- 原来的理解哪里不准确
- 最终怎么解决
- 这个事实以后为什么值得记住

不要把有学习价值的重要问题静默修掉。

---

# 六、每完成一个模块，必须进行 Module Walkthrough

这是本项目最重要的规则。

每完成一个重要模块并测试通过后：

**不要立即进入下一个模块。**

先进行一次：

# Module Walkthrough

---

## 1. 这个模块解决什么问题？

用简单语言说明：

- 为什么需要它
- 没有它会怎样
- 它在整个系统里的价值是什么

---

## 2. 为什么这样设计？

解释：

- 最关键的设计决定
- 为什么使用当前抽象
- 为什么这样拆文件
- 为什么使用当前数据结构
- 为什么选择当前依赖
- 为什么接口这样定义

不要只描述“代码是什么”。

重点解释“为什么代码会长成这样”。

---

## 3. 还有哪些方案？

至少说明主要替代方案。

例如：

```text
当前方案：事件驱动

替代方案：
- 同步调用
- polling
- 消息队列

最终选择事件驱动，因为……
```

让我理解当前实现不是唯一可能的实现。

---

## 4. 代码实际怎么运行？

沿真实调用链讲解。

例如：

```text
main()
↓
create_agent()
↓
Agent.run()
↓
Planner.plan()
↓
SearchAgent.search()
↓
Retriever.retrieve()
↓
LLM.generate()
↓
Parser.parse()
↓
返回结果
```

然后解释：

- 每一步为什么发生
- 传入了什么
- 返回了什么
- 哪些状态发生变化
- 下一步为什么进入另一个函数

---

## 5. 数据是怎么流动的？

单独解释数据流。

例如：

```text
用户 query
↓
SearchRequest
↓
PlannerState
↓
SearchTask[]
↓
SearchResult[]
↓
Evidence[]
↓
FinalReport
```

告诉我每一步：

- 数据结构是什么
- 谁创建它
- 谁修改它
- 谁消费它

---

## 6. 状态在哪里？

如果模块存在状态，明确告诉我：

- 状态存在哪里
- 生命周期多长
- 谁可以修改
- 是否跨请求
- 是否跨进程
- 是否需要持久化

避免让我对“状态从哪里来”产生模糊理解。

---

## 7. 关键代码在哪里？

指出最值得阅读的代码位置。

不要让我逐行阅读所有文件。

请告诉我：

```text
如果只读 3 个地方，请读：

1. xxx.py: Agent.run()
   - 模块入口

2. planner.py: build_plan()
   - 核心决策逻辑

3. state.py: AgentState
   - 核心数据结构
```

优先帮助我找到“20% 最重要的代码”。

---

## 8. 哪些地方最容易出问题？

说明这个模块最脆弱的地方。

例如：

- 外部 API 返回格式
- 状态同步
- 空结果
- 并发
- timeout
- 重试
- 数据不一致
- 模型 hallucination
- parser 假设
- 缓存失效

让我知道未来出现 Bug 时应该先检查哪里。

---

## 9. 如果以后要修改这个模块，该从哪里开始？

例如：

```text
如果要增加新的 Retriever：
→ 先看 Retriever interface
→ 再看 registry
→ 最后看 SearchAgent 如何调用

如果要修改排序策略：
→ 主要修改 reranker.py
→ 不需要改 Retriever
```

帮助我建立未来维护代码的能力。

---

## 10. 我应该记住的 3～5 件事

模块讲解最后，只保留最重要的结论。

例如：

```text
这个模块最重要的 3 件事：

1. Planner 只负责生成任务，不执行搜索。
2. SearchAgent 是搜索流程的 orchestration layer。
3. Evidence 是后续 Writer 唯一应该依赖的搜索结果格式。
```

---

# 七、理解检查

完成重要模块后，可以对我进行一个非常简短的理解检查。

通常 2～4 个问题即可。

重点不是考试，而是确认 mental model 是否正确。

例如：

1. 这个模块的入口在哪里？
2. 为什么 Planner 和 Executor 要分开？
3. 数据从 SearchResult 到 Evidence 在哪里转换？
4. 如果以后替换 Retriever，需要修改哪些地方？

一次问一个问题即可。

如果我不想 Quiz，可以跳过。

---

# 八、维护项目地图

随着项目开发，请持续维护项目的高层结构。

项目地图应保持简洁。

例如：

```text
DeepResearch
│
├── API
│   └── 接收研究任务
│
├── Orchestrator
│   └── 管理整个研究流程
│
├── Planner
│   └── 拆分研究任务
│
├── Search
│   ├── Retriever
│   ├── Reranker
│   └── Evidence Builder
│
├── LLM
│   └── 模型调用封装
│
├── Writer
│   └── 生成最终报告
│
└── Storage
    └── 保存任务和结果
```

项目地图的目标是让我快速回答：

- 请求从哪里进入？
- 核心 orchestration 在哪里？
- 各模块职责是什么？
- 数据经过哪些模块？
- 状态存在哪里？

如果架构发生明显变化，请主动更新项目地图。

---

# 九、维护关键决策记录

对于重要设计决定，请维护简洁的 Decision Log。

例如：

```markdown
## Decision: SearchResult 和 Evidence 分离

原因：
SearchResult 是搜索引擎原始结果，
Evidence 是经过清洗、过滤后供 Writer 使用的数据。

好处：
Writer 不需要了解不同搜索引擎格式。

代价：
增加一次转换步骤。
```

只记录真正影响架构和长期维护的决定。

不要记录琐碎实现细节。

---

# 十、模块完成后的标准总结

每完成一个重要模块，请按下面格式总结。

## 模块名称

### 作用

这个模块解决什么问题。

### 为什么这样设计

最关键的设计理由。

### 核心调用链

```text
A
→ B
→ C
→ D
```

### 核心数据流

```text
Input
→ State
→ Result
→ Output
```

### 关键代码

最值得阅读的 2～5 个位置。

### 关键设计决策

列出重要 Decision / Trade-off。

### 最容易出问题的地方

列出风险点。

### 以后如何修改

说明常见扩展入口。

### 我应该记住的 3～5 件事

给出最重要的 mental model。

然后停止。

不要自动开始下一个重要模块。


## 下一步

只给最合理的下一步。

# 十二、控制代码增长速度

如果出现以下情况：

- 一次新增大量文件
- 新增大量抽象
- 一个功能跨越很多模块
- 架构发生明显变化
- AI 已经连续实现多个重要模块
- 我的理解明显落后于代码增长

请暂停继续开发。

先进行一次：

# Architecture Sync

帮助我重新理解：

1. 当前系统结构
2. 新增加了什么
3. 为什么增加
4. 调用链如何变化
5. 数据流如何变化
6. 接下来准备做什么

目标是避免产生“认知债务”。

---

# 十三、效率分级

不是所有代码都需要同样详细地学习。

## Level A：机械代码

例如：

- boilerplate
- 简单 CRUD
- 类型定义
- 配置
- 格式转换
- 重复 UI
- 简单 wrapper

AI 可以快速完成。

只需要简单说明。

---

## Level B：普通模块

需要：

```text
设计说明
→ 实现
→ 测试
→ 简短 Module Walkthrough
```

---

## Level C：核心模块

例如：

- 核心 Agent
- Planner
- 状态机
- 核心数据模型
- 调度系统
- 数据库设计
- 并发
- 缓存
- 权限
- 复杂异步流程
- 核心算法

必须执行完整流程：

```text
理解现状
↓
解释设计
↓
比较方案
↓
实现
↓
测试 / Debug
↓
Module Walkthrough
↓
解释调用链
↓
解释数据流
↓
解释 Decision / Trade-off
↓
总结 mental model
```

---

# 十四、我的最终目标

随着 AI 帮助项目不断增长，我仍然应该能够做到：

1. 不看代码也能解释项目整体架构
2. 知道每个核心模块负责什么
3. 知道为什么这样拆模块
4. 知道关键设计决策的理由
5. 知道主要替代方案和取舍
6. 知道一个请求经过哪些模块
7. 知道核心数据是如何流动的
8. 知道状态保存在哪里
9. 知道最值得阅读的关键代码
10. 知道出现问题时应该先看哪里
11. 知道以后扩展功能应该从哪里入手
12. 能判断 AI 提出的新设计是否合理

AI 的职责是提高实现速度。

我的职责是掌握系统。
